# 赛事配置生命周期与安全

1. 在 Git 之外根据 [V2 示例](../config/event.example.yaml) 建立每场赛事的 profile。与各站点负责人确认公网 IPv4、运营商与出口、防火墙型号和版本、业务 CIDR、变更窗口及带外管理方式。
2. 在本地运行 `profiles list`、`validate` 和 `plan`。逐条检查双向授权、两条 XFRM 的 ID、站点出口及与现有网络的冲突。以明确的 `-c` 选择本次赛事。
3. 分别为两个站点运行 `export-peer`。由双方管理员核对公网端点、IKE ID 类型、Phase 1/2、业务选择器、路由和 NAT 豁免，再用受控渠道交付各自的参数单。每条链路使用独立的强随机 PSK，由管理员另走独立的安全渠道交付。
4. 后续上线从隔离测试或受控精确路由开始，保留现网 SSH 和带外访问。按 [路线图](roadmap.md) 验证 SA、双向业务、MTU、回程和重协商。若配置外部备网关，分别验收两条路径和双端切换。
5. 结束后归档验收证据、撤销本次赛事的访问和密钥，并按快照清理项目拥有的资源。PR #1 仅完成第 1–3 步所需的离线工具。

## 存储与脱敏

- 建议在 Linux 将真实 profile 存于 root 专用的 `/etc/ipsecvpn/profiles/`，文件权限 `0600`。密钥目录 `/etc/ipsecvpn/secrets/` 使用 `0700`，密钥文件为 root 所有并使用 `0600`。
- `secret_ref` 和通知渠道只接受 `file:/etc/ipsecvpn/secrets/<filename>` 形式。只读命令仅校验引用格式。导出使用 `<SEND_SEPARATELY>`，错误诊断省略配置值。引用文件的权限和存在性留待后续安装预检。
- 参数单和计划有意包含对接所需的地址、网络和设备信息。真实 profile、输出、备份、诊断、PSK、Webhook、登录凭据和赛事敏感参数都应留在受控存储。仓库仅保留虚构样本。
- 上线前由负责人核对授权范围、适用的跨境网络要求与供应商条款。执行环境应保留既有默认路由、SSH、netplan、ufw 和全局 nftables 规则。任何项目管理的系统变更须经过 dry-run、明确确认和可回滚快照。
